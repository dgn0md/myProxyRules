# 动态规则来源与路由方式

本页说明规则数据由哪里来、如何参与路由和 DNS。活动配置仍以 `Script/mihomoScript.js` 为准，静态 YAML 由 GitHub Actions 运行构建器生成并回写；开发者无需本地生成。

维护与换源先遵守 [国内 DNS 白名单维护原则](dns-whitelist.md)。本页记录具体来源；明确域名规则匹配且目标为直连时按规则使用国内 DNS；不能因未命中域名规则后通过 IP 兜底直连，就扩大国内 DNS 的查询范围。

规则模块按 [模块化与动态规则集开发原则](development-principles.md) 设计：优先复用现用上游，核对实际成员后用集合关系控制范围，不逐域名维护同用途清单。

## 其他客户端规则源选择

Mihomo 与 Stash 使用本页所列 MRS、classical 与现有 provider。Surge、Shadowrocket、Quantumult X 通过 `tools/build-targets.js` 的 provider 规则源注册表选择上游文件，顺序固定为：同上游且目标客户端可直接读取、格式及语义已确认的版本；当前已验证的客户端原生来源；否则省略。客户端继续直接更新这些 URL，上游成员不经本仓库转换、筛选、合并或重新发布。

| Provider / Mihomo 上游 | 同上游候选审查 | 目标客户端当前选择 |
| --- | --- | --- |
| `apple_proxy`：Blackmatrix7 Clash YAML | 同一规则仓库提供客户端原生列表，但目标版本与 Clash YAML 的规则类型和成员数量不同，暂不认定为语义已确认的同源等价版本。 | 沿用现有已验证的客户端原生列表作为回退；成员差异不宣称逐条等价。 |
| `apple_cn`：固定版本 SukkaW 文本规则 | 原文件可由 Surge 和 Shadowrocket 作为规则集读取；Quantumult X 没有已确认的同范围文件。 | Surge 与 Shadowrocket 使用同一固定 URL；Quantumult X 省略。 |

## Provider 类别

| Provider 类型    | 典型用途                                                                                       | 路由与 DNS                                                                                                                                                                                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| domain MRS       | Apple、Google、Microsoft、Telegram、Steam、视频、AI 等服务域名。                               | 代理服务的 DNS 请求经路由目标组选择出口；目标为 `直连` 的域名规则使用阿里/腾讯 DoH；`apple` 的连接目标是 `Other Apple Service`，DNS 使用 `Siri Ai/Apple Intelligence` 当前出口；`apple_tv` 的连接与 DNS 都进入 `AppleProxy`。 |
| classical/YAML   | AppleProxy 动态服务成员及固定文本域名规则。                                                    | `apple_proxy` 的域名成员与 DNS policy 进入 `AppleProxy`；其中优先级更高的 Siri/PCC/国际 iCloud 规则保持其既定路由与 DNS。`PROCESS-NAME` 成员只影响连接路由，不生成域名 policy。                                                 |
| ipcidr MRS       | Apple 与 Google、AI（OpenAI）、Microsoft、Telegram、TikTok、Twitter、Meta、Netflix、Spotify 服务 IP。 | IP 规则直接选择服务组；同服务的 domain provider 使用相同出口。IPCIDR provider 本身没有域名 DNS 查询。 |
| domain/classical | 固定文本域名列表、精确/后缀路由和 Emby 关键词等匹配。                                          | 可路由的 domain 与 classical provider 按路由谓词建立 DNS policy；保留集合有专用 policy，关键词规则使用 classical inline set。                                                                                                   |

## 依赖与优先级

- 只保留被路由规则或 DNS policy 实际引用的 provider，避免删除仅供 DNS 使用的集合。
- 通用 `cn` 域名集合不用于国内 DNS 策略或 Fake-IP 过滤，仅在可选 QUIC 豁免规则引用时保留；现有 `geolocation-cn` 独立使用国内 DNS，国内服务开关开启时，13 组国内服务 `AND/NOT` policy 与位于 `geolocation-cn` 之后的 `DOMAIN-SUFFIX,cn,直连`（及 `+.cn` DNS policy）使用国内 DNS；`cn_ip` 继续末端直连兜底。
- `dns_domestic_cdn` 与 `dns_microsoft_cdn` 默认始终开启，独立于普通服务组、极简模式和国内路由开关，同步提供直连路由、代理组 `AND NOT` 排除语句与 `nameserver-policy`；重叠集合及专项例外仍分别生效。
- `dns_microsoft_cdn` 位于前置直连区，且 `Microsoft` 代理规则用 `AND NOT` 排除该集合。`海外游戏` 组内前置 `game_platforms_download_cn`（`category-game-platforms-download@cn`）默认直连并使用国内加密 DNS，同时 `overseas_games`（`category-games-!cn`）通过 `AND NOT` 排除该直连集合。`dns_domestic_cdn` 排在明确海外代理服务组之后、国内厂商与 `geolocation-!cn` 之前，并从 `geolocation-!cn` 中排除。显式主机/后缀 policy 排在所有 rule-set policy 之前，使 Apple/Siri 与 `use-application-dns.net` 在内核中实际优先；广域 `+.cn` policy 排在 `geolocation-cn` 之后，避免抢先覆盖广告、HTTPDNS 或服务集合。
- 移除通用 `direct-nameserver` 及其独立缓存/解析路径；明确目标为 `直连` 的域名规则和动态 domain/classical 规则集使用国内加密 DNS，未命中域名 policy、仅通过 IP 兜底直连的查询仍用默认国外 DNS。普通整厂商集合不自动授权 DNS；国内服务开关开启时，13 组配对集合按与路由相同的 `AND/NOT` 谓词授权，`+.cn` 在 `geolocation-cn` 后生效；`geolocation-cn` 仍单独生效。
- 国内解析例外还包括固定 `apple_cn`、启用模型直连时的四个 Apple CDN 精确域名，以及无合格 Siri 候选时普通 Apple 默认直连的既有解析回退。普通业务查询使用 Cloudflare 强制 DoH-H3 与 Google DoH；代理节点域名使用阿里/腾讯 DoH 并经 `DIRECT` 建连，避免代理启动前依赖境外解析器。`default-nameserver` 启动解析为 Mihomo IP 字面量要求使用阿里/腾讯 IP DoH。
- 缓存和 Fake-IP 减少或延后部分查询，不保证消除真实解析；名单外的国内网站/CDN 可能因国外解析得到不同节点，需要在实际网络测量首次连接和下载表现。
- Apple IP 使用 `apple_ip` 并路由到 `AppleProxy`。该规则排在 `cn_ip` 前面。
- AppleProxy 使用 Blackmatrix7 每日更新的 classical/YAML provider。`apple-tvplus` MRS 保留 TV+ 专属分类，用于补充 AppleProxy 集合未含的 TV+ 成员；两者共享同一组。
- Apple TV+ 使用 Bett `apple-tvplus` 动态 MRS；不再为该集合覆盖的 TV+ 主机添加单独路由。验证样本从实际 provider 快照读取。
- `AI` 只使用 `category-ai-!cn`；共享分析/支持域名没有适合的 AI 服务集合成员边界，不加入 AI 路由。
- 2026-11-19 的规则快照审查未发现 `fsend.cn`、`ctaiot.com`、`international-gfe.download.nvidia.com` 分别适合使用的 `geolocation-cn` / `nvidia@cn` 子集规则，也未发现 `mb3admin.com`、`nubebelle.com` 位于 `category-emby`。保留这些少量现有例外；不以过宽的国家、厂商或整厂商集合替换。
- 私网 IP 使用 `RULE-SET,private_ip,直连,no-resolve`。Google、AI（OpenAI）、Telegram、TikTok、Twitter、Facebook/Meta IP 使用对应代理服务组并加 `no-resolve`；服务组关闭或极简模式下保留这些 IP provider，出口改为 `默认代理`，位于通用 CN IP 兜底之前。
- Apple、Microsoft、Netflix、Spotify IP 规则均加 `no-resolve`，保留各自服务组及其可选出口；此参数不改变代理/直连选择。
- 末端 `RULE-SET,cn_ip,直连,no-resolve` 添加 `no-resolve`，只对纯 IP 与 `fake-ip-filter` 真实 IP 连接提供国内 IP 直连兜底，避免 Fake-IP 下未知海外域名触发本地双重 DNS 解析。
- `no-resolve` 避免为匹配这些 IP 集合而触发域名解析；仍可匹配连接已有的目标 IP。域名路由和 DNS policy 独立生效。
- AI 使用 `category-ai-!cn` 域名集合与 `geoip/openai` 纯 OpenAI IP 集合；不将共享分析/支持域名或共享云/CDN 整段 IP 代入 AI 服务分类。
- 专用 Apple 域名例外排在 Apple CN 与 QUIC 拒绝规则之前。
- 测速地址 `https://www.apple.com/library/test/success.html` 由内核通过被测节点请求；普通 `www.apple.com` 访问遵循现有 Apple 动态规则和 DNS policy，不新增整域代理例外。
- provider 的 IP 与域名集合来自不同数据类别；DNS 侧按域名匹配的 provider 设置策略，不把 IP 地址集合错误地当作 DNS 域名规则。

后续新增、替换或扩容 provider 时，记录用途、格式和实际成员范围，保留客户端直接每日更新方式；不得将通用 `cdn`、整厂商或公共云集合整体加入国内 DNS。

更新某个 provider 时，同时核对路由引用、DNS policy 引用和规则顺序，并在测试中固定 DNS/出口映射，包括 `Other Apple Service` DNS 跟随 Siri 组的约定。
